### 阈值矩阵边界三点全覆盖

验收标准要求「每个阈值取 边界-1 / 边界 / 边界+1 三点全部断言」。实测覆盖：

| 等级 | 分支 | 判定 | 区间侧 | 三点断言 |
|---|---|---|---|---|
| high | `high_demote` | `exp <= 30000` | 内侧 | 29999→降 ✅ · 30000→降 ✅ · 30001→无 ✅ |
| mid | `mid_promote` | `exp >= 30000` | 外侧 | 29999→无 ✅ · 30000→升 ✅ · 30001→升 ✅ |
| mid | `mid_demote` | `exp < 5000` | 内侧 | 4999→降 ✅ · 5000→无 ✅ · 5001→无 ✅ |
| low | `low_promote_2` | `exp >= 30000` | 外侧 | 29999→落升1 ✅ · 30000→升2 ✅ · 30001→升2 ✅ |
| low | `low_promote_1` | `exp >= 10000` | 外侧 | 9999→无 ✅ · 10000→升1 ✅ · 10001→升1 ✅ |
| low | `low_demote` | `exp < 3500` | 内侧 | 3499→降 ✅ · 3500→无 ✅ · 3501→无 ✅ |
| entry | `entry_promote_3` | `exp >= 30000` | 外侧 | 29999→落升2 ✅ · 30000→升3 ✅ · 30001→升3 ✅ |
| entry | `entry_promote_2` | `exp >= 10000` | 外侧 | 9999→落升1 ✅ · 10000→升2 ✅ · 10001→升2 ✅ |
| entry | `entry_promote_1` | `exp >= 3500` | 外侧 | 3499→踢 ✅ · 3500→升1 ✅ · 3501→升1 ✅ |
| entry | `entry_kick` | `exp < 3500` | 内侧 | 3499→踢 ✅ · 3500→不踢 ✅ · 3501→不踢 ✅ |

**边界方向不对称（测试曾在此写错，故特别说明）**：

- **降职/踢出类**区间在边界**内侧**（贡献不足才触发）：`high_demote=30000` 的边界-1（29999）
  **仍然降职**，因为 29999 ≤ 30000 成立。
- **升职类**区间在边界**外侧**（贡献达标才触发）：`mid_promote=30000` 的边界-1（29999）
  **不升职**。
- 因此三点的期望值是：降职类 → (降职, 降职, 无动作)；升职类 → (无动作, 升职, 升职)。

**跨等级同值语义**（原脚本如此，必须继承）：

- `30000` 处：high **降职**（`<=` 含边界），mid **升职**（`>=` 含边界）——同值反向。
- `3500` 处：entry **升职 1 次**（`>=` 含边界），low **无动作**（`<` 不含边界）。
- `3499` 处：entry **踢出**，low **降职**。

测试位置：`tests/test_thresholds.py`（48 项，含 `TestTriggerKeyUniqueness`
验证 10 个阈值键全部可达，防止报告标注失真）。

## 二、硬件交互层（mock 覆盖 + mock 策略）

> 验收标准原文：
> 「【硬件交互层:mock 覆盖 + 单独报告】pyautogui 按键模拟、winsdk OCR、文件轮询 ——
> 以 mock 覆盖分支逻辑与异常路径,**真实设备调用不计入分母**;覆盖率与 mock 策略单独成节报告」

### 覆盖现状

| 模块 | 职责 | 覆盖率 |
|---|---|---|
| `window_input.py` | 窗口查找/置前 + 键名解析 + 模拟人工输入 | 99% |
| `game_state.py` | OCR 界面状态检测（菜单/聊天栏） | 100% |
| `log_watcher.py` | 日志增量监控 + 编码检测 + 响应块提取 | 100% |
| `logger.py` | 6 级分级日志 + 归档 | 100% |

（四个模块补测前分别是 33% / 19% / 62% / 70%。）

### mock 策略（铁律）

| 依赖 | 处理方式 | 为什么 |
|---|---|---|
| `pyautogui.press/hotkey/write` | `unittest.mock.patch` 成记录调用的假函数 | 绝不真实按键——测试跑一次就会真去按键盘 |
| `pyautogui.screenshot` | 注入伪造 Image 对象（`_FakeImage`，返回假 PNG 字节） | 绝不真实截屏 |
| `winsdk.windows.media.ocr.OcrEngine` | 注入伪造 engine，`try_create_from_language` 返回可控 engine 或 None | 绝不调系统 OCR；None 路径专门验证**降级** |
| `pyperclip.copy` | patch + 可控抛异常 | 验证剪贴板被占用时的重试与重试耗尽 |
| `LogWatcher` 的日志文件 | 一律 `tempfile.mkdtemp()` 下的临时文件 | 绝不读真实 `latest.log` |
| `time.sleep` | patch 成 no-op；**通过断言调用参数**验证等待时长取值正确 | 测试秒级完成，且仍验证"等了多久" |
| `ctypes` 窗口操作（`user32.*`） | 通过注入 `hwnd=None` / mock 对象绕过 | 不碰真实窗口句柄 |

### 为什么"真实设备调用不计入分母"

硬件行为（真实按键延迟、OCR 实际识别率、Windows 焦点策略）不可在 CI 环境复现，
且不可重复。把它们计入覆盖率会产生**虚假分数**：跑一次绿、下次因为焦点被抢而红。
所以策略是——**分支逻辑与异常路径用 mock 确定性覆盖**，真实设备行为由人工在
真机验收（不属于 CI 门禁的一部分）。

### 专门覆盖的硬件层业务点

- **OCR 误判防护**（验收第 8 条）：关键词归一化（去空格/全角空格）、多帧采样去抖
  二次确认、缓存复用、OCR 不可用时降级为试探式发送
- **编码检测**：utf-8 / gbk / gb2312 及全失败回退；多处采样防"开头纯 ASCII 误判 utf-8"
- **文件轮转**：`latest.log` 被重建/截断时重新打开
- **`discard_buffer`**：first_command 前丢弃残留，防把上次回显当本次响应
- **暂停门**：暂停期间发送线程阻塞，**零指令发出**（解除暂停后才发）
- **发送互斥**：多线程下模拟输入串行化（最大并发=1，否则剪贴板会串）

### 缺口分析

**缺口高度集中在一个文件**：

| 缺口来源 | 未覆盖行数 | 占全部缺口 |
|---|---|---|
| `main.py`（编排层） | 861 | **95%** |
| 其余全部模块合计 | 45 | 5% |

除 `main.py` 外，所有模块都在 **90% ~ 100%** 区间。

`main.py` 旧实现是一个 640 行的巨型 `main()` 函数，直接在函数体内调用
`pyautogui` / `ctypes` / `input()` / `os.path`，硬件依赖与流程编排缠在一起，
**无法在不真实按键的前提下测到任何分支**——这正是它只有 8% 覆盖率的原因。

### 达标路径

按本轮流程规格重写 `main.py` 为**可注入依赖的阶段化编排**：

- 硬件依赖（窗口查找、按键、日志读取、OCR、用户确认）全部经参数注入
- `input()` 换成可注入的确认回调（返回 True/False）
- 时间源可注入
- 阶段之间清晰分函数，逐阶段可测

## 四、测试有效性保障

验收标准要求「禁止编写无断言或断言恒真的『空测试』；审查阶段须抽查测试有效性」。

采取三道措施：

1. **变异验证**：改坏被测代码的一个分支，确认对应测试**变红**，再改回。
2. **审查者视角抽查**：四个 mock 测试文件由独立复核逐条检查无断言测试、
   只验证 mock 自身的测试、未 patch 的真实设备调用。
3. **断言必须打在业务事实上**：不验证 mock 自己，只验证被测模块对外行为。
