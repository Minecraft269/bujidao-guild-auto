# 日志系统规范

> 日志是本项目的核心可观测手段 —— 异步模式下主线程不读日志、不验证，
> 成败判断完全依赖日志记录的内容。因此日志规格不是「可选优化」，而是硬性要求。
>
> 实现位置：`src/guild_auto/infrastructure/logger.py`；配置项：`config.json` 的 `log` 节。

---

## 一、分级（6 级）

数字越大越详细，**每级包含上一级全部内容**（如 level=5 也会输出 1~4 的内容）。

| 级别 | 名称 | 用途 |
|---|---|---|
| 1 | 致命 Critical | 仅脚本启动失败 / 意外关闭（非用户手动关闭） |
| 2 | 严重错误 Error | 严重错误（含 1） |
| 3 | 错误 Warning | 一般错误与警告（含 1~2） |
| 4 | 信息 Info | 常规运行信息（含 1~3）—— **默认级别** |
| 5 | 调试 Debug | 脚本正在做什么 + 关键返回值：每条命令的发送动作、每次解析的结果、每个决策的输入输出 |
| 6 | 追踪 Trace | 最详细：函数调用链、文件读写、执行位置、线程与队列活动、后台验证全过程 |

### 第 6 级的追踪辅助

第 6 级通过以下辅助函数埋点，缺一即视为实现不完整：

| 函数 | 记录内容 |
|---|---|
| `TRACE_CALL` | 函数进入，含参数快照 |
| `TRACE_RETURN` | 函数返回，含返回值快照 |
| `TRACE_EXCEPTION` | 函数内抛出的异常 |
| `TRACE_FILE_READ` | 读取了哪个文件、多少字节 |
| `TRACE_FILE_WRITE` | 写入了哪个文件、多少字节 |
| `TRACE_LOCATION` | 代码执行到哪个阶段/分支 |

## 二、落盘与轮转

### 文件布局

```
logs/
├── latest.log                 当前运行的日志（UTF-8）
├── app-2026-10-28.gz          本次启动前归档的历史日志（按天）
├── app-2026-10-28-2.gz        同一天的第二份
└── app-2026-10-27.gz          前一天的
```

### 规则

- **主日志**：`logs/latest.log`，UTF-8 编码
- **每次启动归档**：启动时把旧的 `latest.log` 压缩为 `app-YYYY-MM-DD.gz`（压缩包内为 `.log` 文件）
- **同日序号**：同一天内多次启动，自动加序号 `-2.gz` / `-3.gz` ……，**绝不覆盖已有归档**
- **归档失败不阻断启动**：压缩异常时降级为只写 `latest.log` 并记录告警，不能因此导致脚本起不来
- **编码兼容**：Windows 控制台默认 GBK，文件写入固定 UTF-8；控制台输出与文件写入分离，控制台编码异常不得影响文件日志

### 配置

`config.json` 的 `log` 节：

| 键 | 作用 | 可填值 |
|---|---|---|
| `log.enabled` | 是否启用文件日志 | `true` / `false` |
| `log.level` | 日志级别 | `1`~`6` 整数；非法值启动即报错 |
| `log.dir` | 日志目录（相对运行目录） | 目录名，默认 `logs` |

## 三、必须记录的关键事件（11 类）

以下事件**缺一即算实现不完整**。审查时逐类检索日志验证。

| # | 类别 | 必须记录 |
|---|---|---|
| 1 | 启动 | 构建变体名 + 已启用能力清单 + 日志级别 + 配置路径 |
| 2 | 配置 | 加载成功 / 失败；校验错误逐条；热重载触发与结果 |
| 3 | 窗口与 OCR | 窗口查找结果；每次 OCR 识别结论与置信度；菜单检测与 Esc 处理 |
| 4 | 发送 | 每条指令的发送动作；重试次数与原因；**超时告警（超时不得静默）** |
| 5 | 解析 | 面板解析成功条数；解析失败的具体原因 |
| 6 | 异步 | 任务提交 / 开始 / 验证中 / 成功 / 失败 / 重试 / 补做入队 / 队列满丢弃 / 停止排空 |
| 7 | 暂停 | 暂停原因（暂停键 / Ctrl+C / 用户键鼠活动）；恢复后重置了什么 |
| 8 | 决策 | 每条规则 / 阈值的输入值与判定结果；命中哪条规则 |
| 9 | 执行 | 每个动作的成功 / 失败；错误回显原文 |
| 10 | 报告 | 报告文件路径与条数统计 |
| 11 | 退出 | 正常退出 / 异常退出（异常记致命级，含完整 traceback） |

## 四、纪律

- **禁止静默失败**：任何 `except` 分支必须至少记一条 warning，不得只写 `pass`
- **禁止用 `print` 代替日志**：控制台输出统一走 `console()`，它同时写文件
- **级别不可混用**：致命级只用于启动失败与意外关闭，不得用于业务失败
- **隐私**：日志中不得出现真实 QQ 群号、本机绝对路径等敏感信息；玩家名按脱敏规则处理
- **不得刷屏**：同一事件在同一状态下只记一次（例如暂停期间不得每 0.2 秒重复打印）

## 五、验收

| 项 | 方法 |
|---|---|
| 逐级包含 | 分别以 `level=1..6` 运行同一段流程，证明高级别输出包含低级别的全部内容 |
| 第 5 级内容 | 能看清「脚本正在做什么 + 关键返回值」 |
| 第 6 级内容 | 能看到函数调用链、文件读写、执行位置、线程与队列活动 |
| 轮转 | 连续启动多次，生成 `app-YYYY-MM-DD.gz` 且同日序号递增，无覆盖 |
| 关键事件 | 11 类事件逐项在日志中可检索到 |
| 超时可见 | 故意制造超时，确认日志中有告警而非静默 |

## 六、启动与 UI 生命周期埋点（2026-10-31 新增）

> 起因：本地完全体启动后**无界面、无提示、日志停在启动横幅**，仅凭日志无法判断卡在哪一步。
> 本节的目标是一条硬标准：**任何"卡住"都必须能仅凭日志最后 10 行定位到具体阶段。**

### 6.1 阶段埋点（每阶段进入/退出各一条，必须带耗时）

| 阶段 | 必须记录的内容 |
|---|---|
| S0 进程启动 | `argv`、`cwd`、exe 绝对路径、版本号、构建变体、能力清单 |
| S1 配置探测 | 配置路径、是否存在、是否首次运行 |
| S2 配置加载与校验 | 键数量、`config_schema_version`、校验失败逐条 |
| S3 日志系统就绪 | 级别、目录、轮转结果 |
| S4 **UI 入口决策** | `--ui` 值、`ui.enabled` 值、Gui.exe 是否找到（完整路径）、**最终决定：拉起 GUI / 走控制台 / 报错退出**，并写明原因 |
| S5 GUI 进程拉起 | 命令行、PID、等待窗口可见的耗时（超时上限可配） |
| S6 IPC 建立 | 管道名（token 脱敏）、server 就绪耗时、首帧 `hello` 往返耗时 |
| S7 运行环境构建 | `build_runtime` 内 watcher / human / executor / detector / hwnd **每个子步骤**的进入、退出、耗时 |
| S8 游戏窗口查找 | 关键词、命中 `hwnd`、耗时；未命中时记录"等待用户输入" |
| S9 进入主流程 | 操作模式（command/ui）、async 开关、阶段确认粒度 |

行格式示例：

```
[阶段][ENTER] S8 find_game_window keywords=['Minecraft']
[阶段][EXIT ] S8 find_game_window 耗时=0.42s 结果=未命中,转入等待用户输入
```

### 6.2 阻塞点必须可观测

- 所有可能长阻塞的调用（`input`、管道 recv、截图、OCR、文件轮询、子进程 wait）都必须：
  进入前记 INFO（含超时值）→ 返回后记 INFO（含耗时）→ 超时记 WARNING（含已等待时长）。
- **禁止无超时的阻塞等待**；确需无限等待的（如等用户输入）必须在进入前把提示同时写控制台与日志。
- 禁止裸 `except: pass`；catch 分支至少 `log_warning` 并带上被吞掉的异常文本。

### 6.3 看门狗（watchdog）

- 主线程维护"当前阶段"变量；看门狗线程每 10s 检查一次；
  同一阶段持续超过阈值（默认 30s，可配）→ 记 WARNING 并用
  `faulthandler.dump_traceback_later` 把线程栈写进日志。
- 启动后 30s 仍未进入 S9 → 记 ERROR，并在控制台/界面提示
  「启动卡在 <阶段>，日志见 <路径>」。
- 看门狗本身不得阻塞主流程，自身异常不得向上抛。

### 6.4 GUI 侧（Rust）埋点

- 启动参数、管道连接（尝试 / 成功 / 失败 / 重试次数与间隔）、`hello` 收发、
  每次 RPC 的方法名与耗时、窗口创建、托盘创建、关闭流程的每一步。
- GUI 日志与核日志**同一目录**（`logs/` 下，文件名在文档中固定写明），便于按时间对读。

### 6.5 验收

- 人为制造三种卡死：①无游戏窗口且不输入 ②GUI 拉起失败 ③管道不响应，
  分别确认日志**最后 10 行**能指出卡在哪个阶段。
- 启动全程每个阶段都能在日志里查到 `[ENTER]`/`[EXIT]` 与耗时。
- 看门狗在 30s 内触发并产出线程栈。
- UI 入口决策必须显式可见：能回答"为什么没弹出界面"。
