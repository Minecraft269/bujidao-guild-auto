# 详细分析报告规范

> 本项目每次运行结束产出 **三份报告**：
>
> | # | 文件 | 定位 | 读者 |
> |---|---|---|---|
> | 1 | `<日期> <公会名>公会 所有玩家详细贡献.txt` | 全员贡献（原脚本风格） | 群成员 |
> | 2 | `<公会名>_<日期>.txt` | 群公告：升降踢名单 | 群成员 |
> | 3 | **`<日期> <公会名>公会 运行分析报告.txt`** | **本文档定义：完整决策链与运行诊断** | **操作者自己** |
>
> 前两份保持原脚本格式不变（业务规则零改动）。第三份是**新增的独立文件**，
> 只增不改，不影响前两份。

---

## 一、设计目标

回答操作者跑完之后会问的四个问题：

1. **每个人的判定依据是什么？** —— 贡献怎么算的、命中哪个阈值/规则、为什么升降踢
2. **哪些人没处理，为什么？** —— 查询失败、屏蔽词、名单跳过、执行报错，逐人可查
3. **这次跑得怎么样？** —— 各阶段耗时、失败率、OCR/按键试探情况
4. **用的是什么配置？** —— 阈值/开关/名单/文案快照，便于事后复现与追责

**不放进这份报告的内容**：群内公告文案（在第一、二份里）、隐私信息。

---

## 二、文件命名与位置

```
<report_dir>/<YYYY-MM-DD> <安全化公会名>公会 运行分析报告.txt
```

- 目录同其他报告（`config.report_dir`，默认 `reports/`）
- 公会名经 `_safe_guild_name()` 消毒（禁止路径分隔符等）
- 与贡献报告同日同名规则，便于对应查找

---

## 三、报告结构（七节）

### 前置：数据来源按操作模式区分（⚠ 写实现时先看这张表）

| 数据项 | `command` 指令模式 | `ui` UI识别模式 |
|---|---|---|
| 成员名册 | 解析 `/guild list` 日志面板 | 打开公会界面 → 全屏 OCR → **逐页翻页至末页**汇总 |
| 成员总数 | 面板末尾「成员总数: N」 | **可从公会详情 tooltip 读取「人数: [N/M]」**（N=当前人数、M=上限）；<br/>若该 tooltip 不可得，退回「翻页逐页累计」并注明来源 |
| 在线成员数 | 面板末尾「在线成员数: N」 | **界面无此项** → 报告写「不适用（UI 模式无此项）」，不得填 0 或留空 |
| 每人贡献 | `/guild member <名字>` 命令响应 | 点击/悬停成员 → 读界面详情 |
| 通知 | `/gc <文案>` 命令 | 若界面有公会聊天入口则操作；无则报告注明「通知未执行（UI 模式无聊天入口）」 |
| 升/降/踢 | `/guild promote\|demote\|kick` 命令 | 界面内点击对应按钮（升职/降职/踢出） |
| 屏蔽词玩家 | 不发送 `/guild member <星号>`（服务器不响应） | 界面 tip 若能显示真实信息则读取，否则同样跳过 |
| 时间参数 | 命令间隔 / 响应等待 / 重试 | 按键渲染延迟 / OCR 缓存秒数 / 误按阈值 |
| 恢复动作 | OCR 菜单检测 + `first_command` 试探 | 全扫确认界面 + 必要时按键试探重进（**无 first_command**） |

> 原则：**报告里凡是「指令模式专用」的概念（/guild list、/gc、first_command、命令间隔），
> 在 UI 模式下都必须有对应的替代说法或明确标注「不适用」，不得直接照搬。**


### 第 0 节 — 头部元信息

```
=== <公会名>公会 运行分析报告 ===
统计日: 2026-10-17
运行窗口: 2026-10-17 20:14:03 → 2026-10-17 21:07:42  (总耗时 53m39s)

执行人: <管理员>
构建变体: Lite-Async-Gui-Vision        已启用能力: core,async,gui,vision
操作模式: command                       日志级别: 4(信息)

成员总数: 200   在线: 43   实际查询: 189   参与判定: 189
查询成功: 187   查询失败: 2   屏蔽词不可查: 11
```

**要点**：
- 构建变体与能力清单来自运行时能力注册表（缺失能力不打印）
- 操作模式区分 `command` / `ui`
- 计数必须自洽：`成员总数 - 跳过职位 = 实际查询`、`实际查询 = 成功 + 失败 + 屏蔽词`

### 第 1 节 — 阶段耗时与结果

```
--- 一、阶段耗时 ---
阶段             耗时        成功    失败    备注
查询公会列表      0m04s        1       0     第 1 次成功
逐人查询         38m12s      187       2     重试 5 次,最长单人居 3.4s
通知              6m41s      186       1     逐人模式（指令模式=/gc 命令;UI模式=界面操作或不可用）
执行操作          7m52s      124       0     升29/降59/踢36
输出报告          0m01s        3       0
--------------------------------------------
合计             53m39s
```

**要点**：每阶段记录起止时间与成败计数；失败数不为 0 时在「备注」写主要原因。

### 第 2 节 — 逐人决策明细（本报告核心）

按等级分组，**每人多行**（对比贡献报告的一行）：

```
---高活跃（8人）---
[1] <玩家名>
    周贡献: 30528   (每日: 今天 0 / 10-16 30528 / 10-15 0 / 10-14 0 / 10-13 0 / 10-12 0 / 10-11 0)
    加入: 2026-02-11 10:22:31    上次在线: 2026-10-17 19:03(1.2小时前)
    判定: 阈值 high_demote(<=30000) 不满足 → 无操作
    执行: 无操作

[2] <玩家名>
    周贡献: 23746   (每日: 今天 0 / 10-16 23746 / 10-15 0 / ...)
    加入: 2026-05-03 08:11:02    上次在线: 2026-10-16 22:40(1.9天前)
    判定: 阈值 high_demote: 23746 <= 30000 → 降职
    执行: 成功 → 高活跃成员 → 中等活跃成员
```

**要点**：
- **必须写出判定依据**：命中哪条阈值（附带边界语义）或哪条自定义规则（规则名 + 条件表达式），以及输入值
- 执行结果写清 `原等级 → 新等级` 或失败原因原文
- 每日贡献明细来自 `daily` 字段；`今天` 行必须标出（周贡献含今天）
- 被跳过的人也要出现，标注原因（见第 3 节）

### 第 3 节 — 失败与跳过清单

```
--- 三、失败与跳过 ---

  <玩家名> : 同上

  高活跃: 2 人    中等活跃: 3 人    低活跃: 4 人    入门: 2 人
  处理: 指令模式=未发送 /guild member <星号>（服务器不响应该参数）;
        UI模式=界面 tip 若能显示真实信息则读取，否则同样跳过;
        按 blocked_name_policy=skip 跳过
  建议: 可在 UI识别模式下查看其真实名与贡献

黑名单跳过 3 人:
  <玩家A>  <玩家B>  <玩家C>

白名单外跳过 0 人:  （白名单为空时标注「白名单未启用」）

```

**要点**：每类都要有「人数 + 名单/分组 + 原因 + 采用的策略」，不能只写人数。

### 第 7 节 — 全员名册（无遗漏对账）

> **目的**：前六节都是「有事的那些人」。本节列出名册里的**每一个人**，
> 包括被跳过职位、黑名单、白名单外、屏蔽词、查询失败的人 ——
> 保证 `成员总数` 与逐人条目数**逐一对应，零遗漏**，可当作对账清单。
>
> ⚠ **名册来源按操作模式区分（勿混用）**：
> - `command` 模式：`/guild list` 的日志面板解析结果，含「成员总数 / 在线成员数」两行
> - `ui` 模式：打开公会界面 → 全屏 OCR 识别 → **逐页翻页至末页**汇总；
>   **成员总数优先从公会详情 tooltip 读取「人数: [N/M]」**（N=当前人数）；
>   tooltip 不可得时退回「逐页条目累计」，并在报告注明「总数由翻页计数得出」；
>   **在线成员数 UI 界面无此项 → 写「不适用（UI 模式无此项）」**，不得留空或填 0

```
--- 七、全员名册（共 200 人 = 成员总数 200，无遗漏）---
列: 序号 | 玩家 | 周贡献 | 操作 | 状态
状态: 已处理 / 黑名单跳过 / 白名单外跳过 / 保护名单(不踢) / 屏蔽词不可查 /
      查询失败 / 跳过职位(leader/vice_leader/admin)

---会长(1人)---
  001  <玩家名>                    |  ——   |  ——    | 跳过职位

---管理员(1人)---
  002  <玩家名>                    |  ——   |  ——    | 跳过职位

---高活跃(8人)---
  003  <玩家名>                    | 30528 | 无操作  | 已处理
  004  <玩家名>                    | 23746 | 降职    | 已处理
  ...

---中等活跃(N人)---
  ...

---低活跃(N人)---
  ...

---入门(N人)---
  ...

---对账---
  名册条目合计: 200
  成员总数(来源: 指令模式=/guild list 面板末行; UI模式=公会详情 tooltip「人数: [N/M]」): 200
  在线成员数: 43（UI 模式写「不适用」）
  差值: 0  ✅ 无遗漏
  其中: 已处理 124 / 跳过职位 2 / 黑名单 3 / 白名单外 0 /
        屏蔽词 11 / 查询失败 2 / 保护名单(未踢) 5
```

**要点**：
- **顺序与名册来源一致**（指令模式=\`/guild list\` 面板顺序；UI 模式=界面翻页顺序），
  同等级内保持原顺序，便于人工对照
- 序号从 001 连续编到总数，用作对账基准
- 屏蔽词玩家的名字按面板原样输出（全星号），并在状态列标明不可查
- 末尾「对账」段必须显式给出**差值**；差值 ≠ 0 视为报告缺陷（说明解析或统计漏人）
- 编号、列对齐用等宽字符填充，保证纯文本下可读

## 四、实现要求

1. **独立性**：新增 `write_analysis_report(report_dir, guild_name, records, cfg, run_meta)`，
   **不改动**现有 `write_contribution_report` / `write_action_report` 的格式（业务规则零改动）
2. **纯函数优先**：统计计算（分位数、迁移矩阵、计数）抽成 `domain/` 内纯函数，零 IO，可单测
3. **配置驱动**（均需在 `CONFIG_COMMENTS` 注册中文注释）：
   - `report.analysis_enabled`（默认 true）—— 是否生成第三份
   - `report.include_config_snapshot`（默认 true）—— 是否含阈值/开关快照
   - `report.include_daily_detail`（默认 true）—— 是否含每日贡献明细（数据量大时可关）
4. **隐私**：不得出现 QQ 群号、本机路径；玩家名按现有脱敏规则处理
5. **编码**：UTF-8，与现有报告一致
6. **失败不影响主流程**：报告写入失败必须记 warning 并继续，不得让整个运行失败

## 五、验收

- [ ] 三份报告同时产出，前两份格式与改造前**逐字节一致**（回归测试证明）
- [ ] 第三份七节齐全；`command` 模式不输出第六节
- [ ] **全员名册零遗漏**：名册条目数 = 成员总数，对账差值必须为 0；
      被跳过职位 / 黑名单 / 白名单外 / 屏蔽词 / 查询失败的人**都必须出现在名册里**
- [ ] **名册来源按模式正确取得**：
      指令模式=面板解析；UI 模式=逐页翻页汇总 + **公会详情 tooltip「人数: [N/M]」取总数**；
      UI 模式下「在线成员数」写「不适用」而非 0 或留空
- [ ] 若 UI 模式拿不到 tooltip 的总数，退回翻页累计并在报告注明来源，不得直接留空
- [ ] 名册顺序与名册来源一致（同等级内保持原顺序），序号 001~总数连续
- [ ] 计数自洽：`成员总数 - 跳过职位 = 实际查询 = 成功 + 失败 + 屏蔽词`
- [ ] 每个判定过的玩家都能看到「阈值/规则 + 输入值 + 结论」三元组
- [ ] 等级迁移矩阵每行人数之和 = 该等级原有人数
- [ ] `report.analysis_enabled=false` 时不生成第三份，前两份照常
- [ ] 报告目录不可写时：记 warning，运行继续，其余功能正常
- [ ] 统计函数有独立单测，纳入核心层 98% 覆盖率
